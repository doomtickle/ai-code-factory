# Make it yours

The factory works out of the box, but it gets cheaper and more accurate once it
knows your project and your preferences. This guide shows how to give roles
per-project notes, tune each role's model, effort, lanes and session size, add
a role of your own (a docs writer), and keep your own broker settings outside
the repo. For each kind of change, it tells you whether `factory start` is
enough or you need `factory update`.

## Which command applies a change

Settings that are read for every task take effect with `factory start`. Things a
sandbox is created with (its image, kit, project access, and whether it has
broker access at all) need `factory update`, which recreates only the sandboxes
affected, after listing what each one loses and asking you.

| You changed | Run |
|---|---|
| Per-project notes (`projects/<folder>.md`, `projects/<folder>.<role>.md`) | `factory start` |
| A role's instructions, `MODEL`, `MODELS`, `EFFORT`, `LANES`, `MAX_SESSION_TOKENS`, `MAX_TURNS`, `MAX_JOB_SECONDS` | `factory start` |
| A role's `BROKER_TOOLS` (it already had some) | `factory start` |
| A new role, or a removed one | `factory start` |
| A role's `TEMPLATE`, `WORKSPACE` or `kit/`, or whether it has any `BROKER_TOOLS` at all | `factory update` |
| Your local `policy.toml` or `broker-kit/` | `factory update` |
| Only the lane git identity (`[git]` `author_name`, `author_email`) in your local `policy.toml` | `factory start` |
| The Coordinator's default model or briefing (`kits/coordinator/spec.yaml`) | `factory update` |
| `dashboard.toml` (the dashboard's look) | restart `factory dashboard` |

The dashboard's **SETUP** key shows the effective value of each line above and
which of the two commands applies it: see
[Setup](06-dashboard.md#setup-the-configuration-in-force).

> **Tip:** Not sure? `factory start` warns when a sandbox is out of date:
> `out of date (made from an older image or kit): factory-broker; run 'factory update' to recreate them`.
> The dashboard shows the same on its **SERVICE** lamp: amber, "UPDATE due",
> with the sandboxes and why on hover, and the UPDATE key lit. It reads
> "RESTART due" (RESTART lit) when a role override, `enabled-roles` or the
> project notes changed since the last `factory start`.

## Per-project notes

Roles start every task knowing only their instructions and what the Coordinator
tells them. Per-project notes fill the gap: the test command, the layout,
conventions, things not to touch. The file lives in the factory config folder,
outside the project, so the project needs no factory files and no role can
change what it says.

The file name is the project folder's name. For a project in `~/code/my-api`:

```bash
mkdir -p ~/.config/ai-code-factory/projects
$EDITOR ~/.config/ai-code-factory/projects/my-api.md
```

A realistic example:

```markdown
- Stack: TypeScript, Fastify 5, Postgres via Kysely. Node 22. yarn v1
  (`yarn.lock` at the repo root): call `npm_fetch` with path `.`.
- Tests: `factory-test -q -- npx vitest run` (`npm test` starts watch mode).
  One file: `factory-test -- npx vitest run src/server/rate-limit.test.ts`.
- Type check: `factory-test -q -- npx tsc --noEmit`.
- Lint: `factory-test -- npx eslint <files>`.
- Layout: HTTP routes in `src/server/routes/`, business logic in
  `src/domain/`, database access only in `src/db/`.
- Conventions: errors are `AppError` subclasses from `src/domain/errors.ts`;
  never throw plain `Error` from a route.
- Don't edit `src/db/generated/`: it is generated by `yarn codegen`, which
  needs a live database.
- Database tests need Postgres, which the sandboxes don't have: they are
  skipped unless `DATABASE_URL` is set. Say so in reports rather than trying
  to start one.
```

Run `factory start`. It appends the notes to every role's instructions, under a
`# This project (my-api)` heading, and says so:

```text
Added project notes from /Users/you/.config/ai-code-factory/projects/my-api.md to the role instructions
```

For a folder of repositories, use the folder's name (`shop.md` for
`~/code/shop`) and say which notes apply to which repo.

Notes that only one role needs go in `projects/<folder>.<role>.md`, next to the
shared file: `my-api.developer.md` for the docs style and commit conventions,
`my-api.reviewer.md` for what to be strict about in this project. `factory
start` appends each one after the shared notes, to that role alone, under a
`# This project (my-api), for the developer` heading, so the other roles don't
carry it in every prompt.

> **Note:** A role's instructions plus your notes must stay under 20,000
> characters, or the dispatch bridge refuses its tasks with
> `instructions for <role> exceed 20000 characters`. Keep notes to the facts a
> role can't cheaply find on its own.

## Tune a role

Each role is `roles/<name>/role.conf`, a file of plain `KEY="value"` lines.
To tune a role on your machine, don't edit that file: put the keys you want
to change in `~/.config/ai-code-factory/roles/<name>.conf`, a local override
layered over it, outside the repo (see [Local
settings](../../README.md#local-settings)). It survives `git pull`, and keys it
leaves out keep the repo's values. The settings you're most likely to change,
and the only ones an override may set:

| Key | What it does | Developer default |
|---|---|---|
| `MODEL` | Default model: an alias (`sonnet`, `opus`, `haiku`) or a full model id | `claude-sonnet-5-5` |
| `MODELS` | Other models the Coordinator may pick for a single task | `claude-haiku-5-5 opus` |
| `EFFORT` | Default reasoning effort: `low`, `medium`, `high` or `xhigh`; empty is the model's default | empty |
| `LANES` | Tasks the role runs at once, 1 to 8 | `3` |
| `MAX_SESSION_TOKENS` | A lane whose saved session is larger starts the next task fresh; empty is 100000, `0` is no cap | empty |
| `MAX_TURNS` | Turns (tool calls and replies) one job may take before it stops as failed, keeping its session; a safety net against a lost job; empty or `0` is no cap | `200` |
| `MAX_JOB_SECONDS` | Wall-clock seconds one job's `claude` may run before the bridge kills it and marks the job failed (the lane is freed and any partial report is kept); empty is 3600, `0` is no limit | empty |

The developer's `MODEL` and `MODELS` name sonnet and haiku by their full ids,
`claude-sonnet-5-5` and `claude-haiku-5-5`, not the aliases `sonnet` and
`haiku`: the Claude Code CLI in the pinned role image resolves those aliases
to the older `claude-sonnet-5` and `claude-haiku-4-5-20251001`. Opus is left
as the alias: it already resolves to `claude-opus-5-5`.

For example, to make the reviewer cheaper on a low-risk project, run it on
Sonnet by default and keep Opus available for hard reviews:

```conf
# ~/.config/ai-code-factory/roles/reviewer.conf
MODEL="claude-sonnet-5-5"
MODELS="opus"
```

Or, to give the developer a different set of models to pick from per task
(`config.example/roles/developer.conf` has this as a placeholder):

```conf
# ~/.config/ai-code-factory/roles/developer.conf
MODELS="claude-haiku-5-5 opus claude-fable-5-1"
```

Then run `factory start`, which applies overrides: the bridge reads a copy it
takes then, so editing the file mid-session changes nothing until the next
start. The Coordinator's `list_roles` shows the merged result, and `factory
roles` names each role's override file.

An override is checked the same way as `role.conf`, and `factory start` stops
with an error naming the file and key if it sets anything else
(`BROKER_TOOLS`, `WORKSPACE`, `TEMPLATE`, `DESCRIPTION`, ...): what a role may
reach or write changes only in the repo, where it shows in review. A bad
value (a model name with a space, `LANES="9"`) or an override for a role that
isn't in `roles/` stops it too. The file is read as data, never run as a
shell script. `factory doctor` checks overrides as well.

If you're changing a role's defaults for everyone (a contributor's change to
the repo), edit `roles/<name>/role.conf` instead; a change there to `LANES`,
`MODEL` or the other keys above applies from the next task.

The Coordinator's own model is set differently: it defaults to `opus` in
`kits/coordinator/spec.yaml`, and changing that default needs `factory update`,
which recreates the Coordinator and discards its conversation history. To
switch for one session only, type `/model` in the Coordinator's terminal. If you hit
your subscription's usage limits, moving the Coordinator to `sonnet` is the
first thing to try.

See [Roles](../../README.md#roles) for the full list of keys and the default
model for each role.

## Add a role: a docs writer

Roles are data: a folder in `roles/` with a `role.conf`, an `instructions.md`
and a `kit/`. Say you want a role that writes and updates documentation as
branches, so the developer can stay on code.

A docs writer needs to hand back branches, so copy the developer (copying is
the default way to start; without a second argument, `factory role new` copies
the read-only reviewer):

```bash
factory role new docs-writer developer
```

```text
Created roles/docs-writer (copied from developer). Next:
  1. Edit roles/docs-writer/role.conf: DESCRIPTION, WORKSPACE (rw/ro), BROKER_TOOLS, LANES, MODEL and MODELS (optional).
  2. Edit its instructions in roles/docs-writer/instructions.md.
  3. Run 'factory start' again.
```

Edit `roles/docs-writer/role.conf`. The Coordinator reads `DESCRIPTION` to
decide when to use the role, so make it specific. A docs writer needs no
network tools:

```conf
DESCRIPTION="Writes and updates user-facing documentation (README, guides, docstrings) on factory/* branches; doesn't change code"
TEMPLATE="developer"
WORKSPACE="rw"
LANES="1"
BROKER_TOOLS=""
MODEL="claude-sonnet-5-5"
MODELS="claude-haiku-5-5"
EFFORT=""
MAX_SESSION_TOKENS=""
MAX_TURNS="100"
```

Replace `roles/docs-writer/instructions.md`. Keep the branch rules from the
developer's instructions (a `WORKSPACE="rw"` role works in its own clones, and
only committed `factory/*` branches come back) and its fixed "Report" block,
which the Coordinator and the review packet rely on.

```markdown
# Docs writer
You write and update documentation: READMEs, guides, docstrings and code
comments. You don't change program behavior.
- You work in a lane: private git clones of the project. Run `git status`
  first. For new work, `git switch -c factory/<topic> origin/HEAD` (or the base
  the task names). For follow-ups, keep committing to the branch the task names.
- Commit before you report: only committed `factory/*` branches leave your
  sandbox. Say which branch and commit hold the change.
- You see only the user's committed state. If the task assumes changes that
  aren't in the repo, say so instead of guessing.
- Check every command and example you document against the code. If you
  can't verify one, leave it out and say so in your report.
- Plain, precise US English, short paragraphs, second person.
- Keep your report short: the branch, the files changed, and open questions.
```

Then run `factory start`. It creates the `factory-docs-writer` sandbox (the role's
lanes show up in the dashboard's lane view and `factory watch` with the
others), and the Coordinator sees the role the next time it calls
`list_roles`. If it's in the middle of a conversation, mention the new role,
or ask it to check `list_roles`, so it plans with it.

```prompt
Have the docs writer update docs/api.md for the rate limiting merged
yesterday: the 429 response, the Retry-After header and the /healthz
exemption.
```

> **Note:** Each role's kit allows only Anthropic hosts, and that should stay
> so. A role that needs the network gets it through broker tools in
> `BROKER_TOOLS`, which the broker checks against its policy and logs. The kit
> you copied also denies Claude Code's built-in `WebFetch` and `WebSearch`
> through managed settings; keep that unless the new role is a researcher-like
> role that may search (see [Roles](../../README.md#roles)).

To remove a role, delete `roles/<name>/` and run `factory start`. It drops the
role from the dashboard's lane view and `factory watch`,
removes its broker access, and prints the `sbx rm` command for its sandbox;
sandboxes are never deleted automatically.

## Local settings

The repo holds nothing specific to you or your organization. Your settings live
in `~/.config/ai-code-factory/` (`$XDG_CONFIG_HOME/ai-code-factory/` if you set
it), outside every agent's reach. Start from the example and keep only what you
need:

```bash
factory config init
```

It writes the example into that folder with every value commented out, so the
copy changes nothing until you uncomment a line. If any of those files already
exists it writes nothing and exits 1, unless you pass `--force` to overwrite.
Uncomment only the tables and hosts you use (the examples name an
`example.jfrog.io` registry and an `example.atlassian.net` Jira site), then run
`factory doctor` and `factory update`.

`roles/<role>.conf` there tunes a role (see [Tune a role](#tune-a-role)); the
example `roles/developer.conf` is all comments, so it changes nothing until you
uncomment a line. The keys an override may set are exactly `MODEL`, `MODELS`,
`EFFORT`, `LANES`, `MAX_SESSION_TOKENS`, `MAX_TURNS` and `MAX_JOB_SECONDS` (`ROLE_OVERRIDE_KEYS`
in `scripts/lib/roles.sh`); any other key stops `factory start`.

`enabled-roles` there switches on optional roles (today only the researcher,
which is off by default): one role name per line, applied on `factory start`.
It only turns a role on or off; tools and workspace stay in the committed
`role.conf`, and a leftover sandbox of a role you turned off is noted by
`factory doctor`, never removed. See [Roles](../../README.md#roles).

`projects/<project-folder-name>.md` there holds notes for one project (its test
command, say), added to every role's instructions on `factory start`.

`dashboard.toml` there sets the dashboard's nameplate, shift names, CRT and sound
defaults and role colours; the example is all comments. The dashboard reads it
once when it starts, and a mistake makes it ignore the file and say why. See
[Use the dashboard](06-dashboard.md#your-own-look-dashboardtoml). It changes how
the page looks and nothing else, so it needs neither `factory update` nor a
restart of the factory, only of `factory dashboard`.

`plugins/<module>/` there holds broker plugins: Python packages that add tools
to the gateway (the broker's `docs/plugin-tools.md` describes the format).
`factory update` copies the folder into the broker image, and the broker
sandbox imports each folder name as a module. A plugin runs inside the broker,
so add only code you wrote or reviewed. `BROKER_TOOLS` in a `role.conf` accepts
only the names in `broker/tools.txt`, so a role can't be granted a plugin's tool
that way. `factory status` counts the folder as local settings.

`policy.toml` there overlays the repo's `broker/policy.toml` table by table: a
key you set replaces the repo's value, and keys you leave out keep it. A list
is replaced as a whole, so to add a host you repeat the ones you want to keep.

For example, to let the researcher (once enabled) read the Fastify docs, set the
full list in your local `policy.toml`:

```toml
[web]
allow_hosts = [
  "docs.python.org",
  "developer.mozilla.org",
  "nodejs.org",
  "pypi.org",
  "www.npmjs.com",
  "fastify.dev",
]
```

The broker sandbox's own network policy must allow the new host too, so add it
to your local `broker-kit/spec.yaml` (the example has the full file;
keep its header and replace the hosts under `allow`):

```yaml
permissions:
  network:
    allow:
      - fastify.dev
```

Then rebuild the broker image and recreate the broker sandbox:

```bash
factory update
```

`factory doctor` then checks that every host the policy can reach is in a
broker kit, and names any that aren't.

> **Warning:** Recreating the broker sandbox deletes a GitHub token set by hand
> with `sbx secret set github --sandbox factory-broker`, and any credential you
> delivered with `factory secret set`. Credentials saved with
> `factory secret save` (the GitHub token included) come back by themselves on
> the next broker start; for the rest, `factory update` tells you before it removes
> anything, and the run that creates the new broker lists what to set again.

`[git]` `author_name` and `author_email` in the same `policy.toml` set the git
identity of the developer's lane commits (default `factory-<lane>
<<lane>@factory.invalid>`; `{lane}` stands for the lane's name). The dispatch
bridge reads them, not the broker, so `factory start` applies them. See
[Getting the developer's work](../../README.md#getting-the-developers-work).

The same folder holds your `[git].repos` for pushes, a private npm registry and
your Jira site. See [Local settings](../../README.md#local-settings) and the
"Enabling" sections after it.
