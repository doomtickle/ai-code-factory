# Make it yours

The factory works out of the box, but it gets cheaper and more accurate once it
knows your project and your preferences. This guide shows how to give roles
per-project notes, tune each role's model, effort, lanes and session size, add
a role of your own (a docs writer), and keep your own broker settings outside
the repo. For each kind of change, it tells you whether `factory start` is
enough or you need `factory update`.

## Which command applies a change

Settings that are read for every task take effect with `factory start`. Things a
sandbox is created with (its image, kit, project access, and whether it has
broker access at all) need `factory update`, which recreates only the sandboxes
affected, after listing what each one loses and asking you.

| You changed | Run |
|---|---|
| Per-project notes (`projects/<folder>.md`) | `factory start` |
| A role's instructions, `MODEL`, `MODELS`, `EFFORT`, `LANES`, `MAX_SESSION_TOKENS` | `factory start` |
| A role's `BROKER_TOOLS` (it already had some) | `factory start` |
| A new role, or a removed one | `factory start` |
| A role's `TEMPLATE`, `WORKSPACE` or `kit/`, or whether it has any `BROKER_TOOLS` at all | `factory update` |
| Your local `policy.toml` or `broker-kit/` | `factory update` |
| The Coordinator's default model or briefing (`kits/coordinator/spec.yaml`) | `factory update` |

> **Tip:** Not sure? `factory start` warns when a sandbox is out of date:
> `out of date (made from an older image or kit): factory-broker; run 'factory update' to recreate them`.

## Per-project notes

Roles start every task knowing only their instructions and what the Coordinator
tells them. Per-project notes fill the gap: the test command, the layout,
conventions, things not to touch. The file lives in the factory config folder,
outside the project, so the project needs no factory files and no role can
change what it says.

The file name is the project folder's name. For a project in `~/code/my-api`:

```bash
mkdir -p ~/.config/ai-code-factory/projects
$EDITOR ~/.config/ai-code-factory/projects/my-api.md
```

A realistic example:

```markdown
- Stack: TypeScript, Fastify 5, Postgres via Kysely. Node 22. yarn v1
  (`yarn.lock` at the repo root): call `npm_fetch` with path `.`.
- Tests: `factory-test -q -- npx vitest run` (`npm test` starts watch mode).
  One file: `factory-test -- npx vitest run src/server/rate-limit.test.ts`.
- Type check: `factory-test -q -- npx tsc --noEmit`.
- Lint: `factory-test -- npx eslint <files>`.
- Layout: HTTP routes in `src/server/routes/`, business logic in
  `src/domain/`, database access only in `src/db/`.
- Conventions: errors are `AppError` subclasses from `src/domain/errors.ts`;
  never throw plain `Error` from a route.
- Don't edit `src/db/generated/`: it is generated by `yarn codegen`, which
  needs a live database.
- Database tests need Postgres, which the sandboxes don't have: they are
  skipped unless `DATABASE_URL` is set. Say so in reports rather than trying
  to start one.
```

Run `factory start`. It appends the notes to every role's instructions, under a
`# This project (my-api)` heading, and says so:

```text
Added project notes from /Users/you/.config/ai-code-factory/projects/my-api.md to the role instructions
```

For a folder of repositories, use the folder's name (`shop.md` for
`~/code/shop`) and say which notes apply to which repo.

> **Note:** A role's instructions plus your notes must stay under 20,000
> characters, or the dispatch bridge refuses its tasks with
> `instructions for <role> exceed 20000 characters`. Keep notes to the facts a
> role can't cheaply find on its own.

## Tune a role

Each role is `roles/<name>/role.conf`, a file of plain `KEY="value"` lines.
The settings you're most likely to change:

| Key | What it does | Developer default |
|---|---|---|
| `MODEL` | Default model: an alias (`sonnet`, `opus`, `haiku`) or a full model id | `sonnet` |
| `MODELS` | Other models the Coordinator may pick for a single task | `haiku opus` |
| `EFFORT` | Default reasoning effort: `low`, `medium`, `high` or `xhigh`; empty is the model's default | empty |
| `LANES` | Tasks the role runs at once, 1 to 8 | `3` |
| `MAX_SESSION_TOKENS` | A lane whose saved session is larger starts the next task fresh; empty is 100000, `0` is no cap | empty |

For example, to make the reviewer cheaper on a low-risk project, run it on
Sonnet by default and keep Opus available for hard reviews:

```conf
# roles/reviewer/role.conf
MODEL="sonnet"
MODELS="opus"
```

Or, to keep developer sessions small on a project with long, unrelated tasks:

```conf
# roles/developer/role.conf
MAX_SESSION_TOKENS="60000"
```

Then run `factory start`. Every change above applies from the next task.

The Coordinator's own model is set differently: it defaults to `opus` in
`kits/coordinator/spec.yaml`, and changing that default needs `factory update`,
which recreates the Coordinator and discards its conversation history. To
switch for one session only, type `/model` in the Coordinator pane. If you hit
your subscription's usage limits, moving the Coordinator to `sonnet` is the
first thing to try.

See [Roles](../../README.md#roles) for the full list of keys and the default
model for each role.

## Add a role: a docs writer

Roles are data: a folder in `roles/` with a `role.conf`, an `instructions.md`
and a `kit/`. Say you want a role that writes and updates documentation as
branches, so the developer can stay on code.

A docs writer needs to hand back branches, so copy the developer (copying is
the default way to start; without a second argument, `factory role new` copies
the read-only reviewer):

```bash
factory role new docs-writer developer
```

```text
Created roles/docs-writer (copied from developer). Next:
  1. Edit roles/docs-writer/role.conf: DESCRIPTION, WORKSPACE (rw/ro), BROKER_TOOLS, LANES, MODEL and MODELS (optional).
  2. Edit its instructions in roles/docs-writer/instructions.md.
  3. Re-run ./scripts/02-launch-factory.sh <project-dir>.
```

Edit `roles/docs-writer/role.conf`. The Coordinator reads `DESCRIPTION` to
decide when to use the role, so make it specific. A docs writer needs no
network tools:

```conf
DESCRIPTION="Writes and updates user-facing documentation (README, guides, docstrings) on factory/* branches; doesn't change code"
TEMPLATE="developer"
WORKSPACE="rw"
LANES="1"
BROKER_TOOLS=""
MODEL="sonnet"
MODELS="haiku"
EFFORT=""
MAX_SESSION_TOKENS=""
```

Replace `roles/docs-writer/instructions.md`. Keep the branch rules from the
developer's instructions: a `WORKSPACE="rw"` role works in its own clones, and
only committed `factory/*` branches come back.

```markdown
# Docs writer
You write and update documentation: READMEs, guides, docstrings and code
comments. You don't change program behavior.
- You work in a lane: private git clones of the project. Run `git status`
  first. For new work, `git switch -c factory/<topic> origin/HEAD` (or the base
  the task names). For follow-ups, keep committing to the branch the task names.
- Commit before you report: only committed `factory/*` branches leave your
  sandbox. Say which branch and commit hold the change.
- You see only the user's committed state. If the task assumes changes that
  aren't in the repo, say so instead of guessing.
- Check every command and example you document against the code. If you
  can't verify one, leave it out and say so in your report.
- Plain, precise US English, short paragraphs, second person.
- Keep your report short: the branch, the files changed, and open questions.
```

Then run `factory start`. It creates the `factory-docs-writer` sandbox and a
**docs-writer** tab, and the Coordinator sees the role the next time it calls
`list_roles`. If it's in the middle of a conversation, mention the new role,
or ask it to check `list_roles`, so it plans with it.

```prompt
Have the docs writer update docs/api.md for the rate limiting merged
yesterday: the 429 response, the Retry-After header and the /healthz
exemption.
```

> **Note:** Each role's kit allows only Anthropic hosts, and that should stay
> so. A role that needs the network gets it through broker tools in
> `BROKER_TOOLS`, which the broker checks against its policy and logs.

To remove a role, delete `roles/<name>/` and run `factory start`. It closes the
role's tab, removes its broker access, and prints the `sbx rm` command for its
sandbox; sandboxes are never deleted automatically.

## Local settings

The repo holds nothing specific to you or your organization. Your settings live
in `~/.config/ai-code-factory/` (`$XDG_CONFIG_HOME/ai-code-factory/` if you set
it), outside every agent's reach. Start from the example and keep only what you
need:

```bash
mkdir -p ~/.config/ai-code-factory
cp -R config.example/. ~/.config/ai-code-factory/
```

The copied files hold placeholder values (an `example.jfrog.io` registry, an
`example.atlassian.net` Jira site). Delete the tables and hosts you don't use
before you run `factory update`.

`policy.toml` there overlays the repo's `broker/policy.toml` table by table: a
key you set replaces the repo's value, and keys you leave out keep it. A list
is replaced as a whole, so to add a host you repeat the ones you want to keep.

For example, to let the researcher read the Fastify docs, set the full list in
your local `policy.toml`:

```toml
[web]
allow_hosts = [
  "docs.python.org",
  "developer.mozilla.org",
  "nodejs.org",
  "pypi.org",
  "www.npmjs.com",
  "fastify.dev",
]
```

The broker sandbox's own network policy must allow the new host too, so add it
to your local `broker-kit/spec.yaml` (the copied example has the full file;
keep its header and replace the hosts under `allow`):

```yaml
permissions:
  network:
    allow:
      - fastify.dev
```

Then rebuild the broker image and recreate the broker sandbox:

```bash
factory update
```

`factory doctor` then checks that every host the policy can reach is in a
broker kit, and names any that aren't.

> **Warning:** Recreating the broker sandbox deletes a GitHub token stored with
> `--sandbox factory-broker`, and any credential you delivered with
> `factory secret set`. `factory update` tells you before it removes anything,
> and the run that creates the new broker lists what to set again.

The same folder holds your `[git].repos` for pushes, a private npm registry and
your Jira site. See [Local settings](../../README.md#local-settings) and the
"Enabling" sections after it.
